Every decision behind Beacon, and why it was made that way.

Beacon is a webhook delivery platform built from scratch across 13 phases: ingestion, an async delivery queue, retries, idempotency, concurrency-safe workers, a dead-letter queue, request signing, rate limiting, a live dashboard, containerization, real load testing, and a live AWS deployment. This document exists so every tool choice, every tradeoff, and every bug found along the way can be explained cold, not recited.

13 phases · ~700 lines of application code · 3 real production bugs found & fixed under load · Deployed live on AWS EC2

Foundations

Stack & tool choices

Every tool below was picked for a specific reason, not by default. Here's the reasoning for each.

Python + FastAPI

FastAPI was chosen over Flask and Django. Flask has no built-in request validation or async support without extra libraries bolted on. Django is a full batteries-included web framework (templating, admin panel, ORM baked in) that's heavier than a focused API service needs. FastAPI gives automatic request validation from Python type hints (via Pydantic), automatic interactive API docs (the /docs Swagger UI came for free, no extra work), and native async support, for roughly the same amount of code as Flask.

Uvicorn

FastAPI only defines how to respond to a request; it doesn't listen on a network socket by itself. Uvicorn is the actual ASGI server process that accepts TCP connections, parses HTTP, and calls into the FastAPI app. This split (framework vs. server) is the same shape as Django+Gunicorn or Rails+Puma.

PostgreSQL

A relational database was chosen specifically because this project needs real transactional guarantees: idempotency keys rely on a database-level unique constraint (not just an application check) to be safe under concurrent duplicate requests, and event status + delivery attempt logging need to commit atomically together. Postgres's JSONB column type also let the event payload stay schema-flexible (any JSON shape) while everything else about the event stayed properly relational and queryable.

SQLAlchemy

Used as the ORM instead of writing raw SQL by hand, mainly for connection pooling control. That pooling configuration (pool_size, max_overflow) became directly relevant during load testing — the default pool size was one of three real bottlenecks found under concurrent load (see Phase 12).

Redis

Redis does three distinct jobs in this architecture, which is exactly why it was chosen over a heavier dedicated message broker like RabbitMQ, AWS SQS, or Kafka:

  • A list (LPUSH/BRPOP) as the main delivery queue — simple FIFO, no need for Kafka-style partitioned ordering or SQS-style visibility timeouts at this scale.
  • A sorted set as a delay mechanism for scheduling retries — score by the timestamp a retry becomes due, which a plain list can't express at all.
  • Atomic counters (INCR) for the rate limiter — race-free without any extra locking.

One in-memory store covering all three roles kept the architecture simple. RabbitMQ or Kafka would have added real operational complexity (clustering, topic/exchange configuration) that this project's actual scale never justified.

Next.js + TypeScript

The dashboard is a small, single-page, client-heavy app — a plain React SPA (via Vite, say) would have worked too, but Next.js's built-in dev server, file-based routing, and production build pipeline meant less setup for the same result. TypeScript catches type mistakes (like a mismatched API response shape) at compile time instead of at runtime in a user's browser.

Docker + Docker Compose

Every service (API, worker, Postgres, Redis, dashboard) runs in its own container, defined in one docker-compose.yml. This makes the whole system reproducible with a single command on any machine, and is also literally how it's deployed to AWS — the same file that runs locally runs in production.

AWS EC2

EC2 was chosen over AWS Lambda specifically because this system has a persistent background process — the worker sits in a loop polling Redis, which doesn't fit serverless's request-in/response-out model at all. EC2 was chosen over ECS/Fargate (container orchestration services) because a single EC2 instance running Docker Compose is functionally identical for a project at this scale, without needing to learn or configure a separate orchestration layer, task definitions, or a load balancer.

Locust

Locust is Python-native, so load-testing scripts live in the same language as the rest of the project, versus k6 (JavaScript) or JMeter (XML config, GUI-first). It also generates real percentile latency reports (p50/p95/p99) out of the box.

GitHub Actions

Free, and tied directly to the GitHub repo with no separate CI service to configure or pay for.

Phase 1

Ingestion: FastAPI → PostgreSQL

POST /events validates a request and persists it. No queue yet — the simplest possible slice that could be tested end to end.

Decision

UUIDs were used as primary keys instead of auto-incrementing integers. An auto-increment ID requires a round-trip to the database to know the "next" value, which becomes a real bottleneck once multiple processes (API replicas, workers) are inserting concurrently. A UUID can be generated client-side or worker-side with no coordination at all.

Decision

The event payload is stored as JSONB rather than plain text. Postgres can index and query inside a JSONB column later (e.g. "find every event where payload.type = order.created") without deserializing every row in application code first.

Decision

Two separate Pydantic schemas exist — EventCreate for what a client is allowed to send, and EventOut for what gets returned — instead of reusing the database model directly. This is a deliberate boundary: a client should never be able to set status or id on creation; the server owns those.

Request lifecycle

  1. Uvicorn accepts the TCP connection and parses the HTTP request.
  2. Pydantic validates the JSON body against EventCreate — a malformed request is rejected here, before any application code runs.
  3. FastAPI's dependency injection (Depends(get_db)) hands the route a database session, and guarantees it's closed afterward via a finally block, even if the request raises an exception.
  4. The event is inserted and committed; the response is serialized through EventOut.

Phase 2

The Redis queue

After saving to Postgres, the event's ID gets pushed onto a Redis list. This is the single most important architectural decision in the whole project.

Decision

Why a queue at all: without one, POST /events would have to make the actual HTTP call to the destination synchronously. A slow or hung destination server would then make the ingestion API itself hang. The queue means "accept the event" and "deliver the event" are decoupled — a dead downstream server can never block ingestion.

Decision

Only the event ID is queued, not the full payload. Postgres stays the single source of truth; if the two ever needed to be inspected or reconciled, there's one place to look, not two that could drift out of sync.

Decision

LPUSH (push left) paired with BRPOP (pop right) makes this a FIFO queue. Pushing and popping from the same end would make it LIFO — under a burst of traffic, old events could get starved indefinitely behind a constant stream of new ones.

Phase 3

The worker & real delivery

A separate, standalone Python process that pulls jobs off the queue and does the actual HTTP delivery.

Decision

The worker is a fully separate process from the API, not a background thread inside it. This means the API and the delivery pipeline can scale independently — more delivery volume means running more worker replicas, without touching the API at all.

Decision

requests.post(..., timeout=10) — without an explicit timeout, a destination that accepts the connection but never responds would hang the worker forever, since the worker processes one job at a time.

Decision

Failures are split into two distinct cases: response.ok being false (the destination responded, but with an error status) versus a caught requests.RequestException (no response was ever received at all — DNS failure, connection refused, or the timeout firing). These get logged differently: the first has a real response_status; the second has none, but does have an error message.

Decision

time.monotonic() is used to measure delivery latency, not time.time(). The wall clock can jump backward (NTP sync, DST, manual changes) and produce a negative duration; a monotonic clock is guaranteed to only move forward.

Phase 4

Retries with increasing backoff

A failed delivery isn't permanent after one try. It's retried up to 4 attempts total, with increasing delay between them: 5s, then 30s, then 120s, before dead-lettering.

Decision

A Redis sorted set schedules delayed retries, scored by the unix timestamp each one becomes due. A plain list has no concept of "wait until later" — a sorted set lets the worker ask "what's due right now?" in one call (ZRANGEBYSCORE).

Decision

The queue payload changed from a bare event ID to a small JSON object ({event_id, attempt_number}). Once retries exist, the queue needs to carry the attempt count forward too — a bare ID alone would lose that information every time a job got re-queued.

Decision

A fixed backoff schedule was used instead of a pure exponential formula. It's predictable, easy to reason about, and easy to demo — a formula with no cap could in theory grow the wait time unboundedly.

Phase 5

Idempotency keys

A client can safely retry a POST /events call (say, after a network timeout where it's unsure the first attempt landed) without creating a duplicate event, by sending an Idempotency-Key header — the same pattern Stripe and GitHub use.

Decision

The real safety net is a database-level unique constraint on the idempotency key column, not just an application-level "check if it exists first" query. A check-then-insert has a race condition: two identical requests arriving at the exact same instant could both pass the check before either has committed. The unique constraint makes Postgres itself reject the second insert, which gets caught and turned into "return the existing row" instead.

Decision

Postgres allows multiple NULL values under a unique constraint (NULLs are never considered equal to each other in SQL), so events created without an idempotency key are completely unaffected by this constraint.

Phase 6

Concurrency safety

Can two workers ever claim and deliver the same job? This phase found a real bug proving the answer was briefly "yes."

Bug found

The retry-promotion logic did ZRANGEBYSCORE (read what's due) followed by ZREM (delete it) as two separate Redis calls. If two workers called this at the same instant, both could see the same due retry before either removed it — and both would push it onto the delivery queue, causing the same event to be delivered twice to a real destination.

Fix

Use ZREM's own return value (0 or 1, however many members it actually removed) as an atomic "did I win the claim" check. Only push the job forward if the removal actually succeeded. Whichever worker's delete call wins is the only one that proceeds — the delete operation itself doubles as the claim.

BRPOP on the main delivery queue was already safe without any changes — Redis guarantees only one caller ever receives a given list item, no matter how many workers are calling BRPOP concurrently.

Known limitation

If a worker crashes after BRPOP removes a job from the queue but before it finishes processing, that job is simply gone — no other worker will ever see it again. A production-grade fix would use a "visibility timeout" pattern: move the job into a per-worker in-progress list on pop, only remove it for good after a successful commit, and sweep stale in-progress jobs back onto the queue after a timeout. This wasn't implemented; it's a legitimate answer to "what would you improve given more time."

Phase 7

Dead-letter queue

An event that exhausts all 4 retry attempts doesn't just disappear into a failed status buried in a table — it becomes something explicitly visible and recoverable.

Decision

Two things happen on final failure: the event's ID goes onto a dedicated Redis list (dead_letter_queue, an operational signal), and GET /events/dead-letter queries Postgres directly for anything with status = "failed" (the reliable source of truth for actually listing them). A manual replay endpoint, POST /events/{id}/retry, resets the event to pending and re-queues it from attempt 1.

The real-world motivation: if a customer's server is down for an hour during a deploy, any webhook that fails during that window shouldn't be lost forever once it exhausts retries. Once they fix their server, the failed events can be found and replayed.

Phase 8

HMAC request signing

Every delivery includes an X-Beacon-Signature header so the receiving server can verify the request genuinely came from Beacon and wasn't forged or tampered with in transit.

Decision

The payload is serialized to bytes exactly once, and those exact bytes are both signed and sent as the literal request body — instead of signing a Python dict and letting the HTTP client serialize it separately. Two independent serializations of "the same" data aren't guaranteed to produce byte-identical output (key ordering, spacing), and a receiver re-hashing the raw bytes it actually received would then fail verification even though nothing was actually wrong.

Scope simplification

A production multi-tenant system would use a secret per registered destination (the way Stripe does — one webhook secret configured once per endpoint in your dashboard, reused for every event sent there). Beacon has no endpoint-registration concept, so a single global signing secret is used for the whole instance. Worth being able to say out loud as a deliberate scope choice, not an oversight.

Phase 9

Rate limiting

A fixed-window counter, applied per client IP, protects the ingestion API from being hammered.

Decision

A fixed-window counter (INCR + EXPIRE) was used instead of a token bucket, deliberately, right after the Phase 6 lesson. INCR is atomic in Redis, so this stays race-free under concurrent requests from the same IP with zero extra locking. A token bucket's read-modify-write cycle would reintroduce the exact class of race that Phase 6 found and fixed.

The tradeoff: fixed windows allow a small burst right at the window boundary (e.g. 20 requests at :59 and another 20 at :00 — 40 in about a second). A sliding window or true token bucket smooths that out, but needs a Lua script to stay atomic. That tradeoff is a legitimate, informed choice for this project's scale.

Bug found (Phase 12)

The rate limit override used for load testing (RATE_LIMIT_MAX_REQUESTS=100000) was accidentally left as a permanent default in the deployment config, which meant the live AWS deployment had rate limiting effectively disabled for anyone, silently. Caught during a final review pass and fixed by removing the override from the default config entirely — it's now something deliberately re-added only for the duration of an actual load test, then removed again.

Phase 10

The dashboard

A live view of event status, success rate, and latency — polling every 4 seconds.

Decision

Deliberately designed to avoid the generic "AI-built dashboard" look (gradient hero cards, glassmorphism, an indigo/purple default palette). Typography uses IBM Plex Sans for interface labels and IBM Plex Mono specifically for data values (status, IDs, timestamps, latency numbers) — that split is functional, not decorative: mono marks "this is a real data value," sans marks interface chrome.

The GET /stats endpoint computes success rate and average latency with real SQL aggregates (AVG() over the delivery attempts table), not client-side math over a fetched list.

Phase 11

Docker: the whole stack, one command

API, worker, dashboard, Postgres, and Redis all run as containers, defined in one docker-compose.yml. A sixth service, the load-testing fake receiver, lives in the same file but sits behind a Compose profile so it never starts as part of the normal stack.

Decision

The dashboard's Docker build uses 3 stages (deps → builder → runner). The final image only copies in the built output and production node_modules, not the full Node dev toolchain used to build it — smaller image, no leaked build-time tooling.

Decision

Containers reach each other by Docker Compose service name (postgres, redis), never localhost. Inside a container, localhost means that container itself, not a sibling container. The one exception: the dashboard's browser-side fetch calls correctly still use the externally-reachable host, because that code executes in the viewer's browser on the host machine, not inside the Docker network.

Fix

ENV PYTHONUNBUFFERED=1 in the Dockerfile. Python fully buffers stdout when it isn't attached to a real terminal, which meant worker logs were silently invisible in docker compose logs until enough output accumulated to force a flush — a real, repeatedly-annoying debugging obstacle during development, fixed with one line.

Phase 12

Load testing: found real bugs, not just numbers

Built a Locust load test and a deliberately flaky fake receiver (80% success / 10% error / 5% slow / 5% disconnect) to generate real numbers under real failure conditions — and along the way, found four genuine production bugs.

Bug 1 — connection pool exhaustion

create_engine(DATABASE_URL) never configured a pool size, so SQLAlchemy used its default: 5 base connections + 10 overflow = 15 max. Under 500 concurrent producers, requests beyond that ceiling queued for a connection and hit SQLAlchemy's default 30-second wait timeout, which showed up as response times clustering at exactly 30000–31000ms before failing with a 500. Confirmed directly in the logs: QueuePool limit of size 5 overflow 10 reached, connection timed out, timeout 30.00.

Fix

Explicitly sized the pool (pool_size, max_overflow), then rebalanced per-process once multiple uvicorn processes were added (each process gets its own independent pool, so 4 processes × a pool sized for one process could exceed Postgres's own connection ceiling).

Bug 2 — single-process saturation

Even with the pool fixed, a single uvicorn process's internal thread pool (used to run synchronous route handlers) saturated under load — and backed up unrelated traffic too: the dashboard's own background polling started hanging behind the load test's requests, since everything shared one process's limited thread pool.

Fix

Ran uvicorn with --workers 4 — 4 separate OS processes sharing the load instead of one.

Bug 3 — the real one: a multi-replica deadlock

Every worker container ran schema setup (Base.metadata.create_all()) at startup. Scaling to 8 worker replicas at once (docker compose up -d --scale worker=8) meant all 8 tried to run that DDL check simultaneously — and Postgres genuinely deadlocked between them: psycopg2.errors.DeadlockDetected. Worse, nothing caught that exception in the worker's main loop, so it crashed the process outright, and with no restart policy configured, all 8 workers silently died and stayed dead. The delivery pipeline had completely stopped with zero indication why — it just looked stalled.

Fix (three parts)
  • Removed schema creation from the worker entirely — it now lives only in the API, run exactly once.
  • Wrapped the per-job processing call in a try/except, so one bad job (a deadlock, a network blip, anything) gets logged and skipped instead of crashing the whole process.
  • Added restart: unless-stopped as defense-in-depth, in case something else unexpected still slips through.
Bug 4 — event creation and queueing aren't atomic

Found by comparing Locust's own tracked request count against the actual row count in Postgres after a test: 33 events (1.4% of a 2,443-event batch) were committed to the database but never entered the Redis queue at all — zero delivery attempts, and both Redis queues confirmed empty, so nothing was left to process them. Saving an event to Postgres and pushing it onto the queue are two separate steps in create_event, not one atomic operation. An interruption between them — here, tied to the test harness (Locust) abruptly cutting off in-flight requests at the run's time limit — can silently orphan an event before it's ever queued for delivery.

Not fixed

Documented as a known limitation rather than fixed — a real fix would need something like an outbox pattern (write the "needs queueing" intent in the same transaction as the event, with a separate process guaranteeing it eventually gets queued) or wrapping both steps so a failure after the DB commit gets retried. Good "what would you improve" interview answer, same category as the worker crash-recovery gap.

Phase 13

AWS deployment

Everything up to this point only ever ran on a laptop. This phase proves it runs on a real server anyone could reach over the internet.

Decision

A t3.small EC2 instance (Ubuntu), not a bigger/managed setup — the goal was proving deployability, not re-running the load test against the cloud. RDS/ElastiCache (managed Postgres/Redis) were deliberately skipped in favor of running them as containers on the same instance via the same docker-compose.yml already used locally — simpler, and the whole point was reusing the existing recipe, not building separate cloud-native infrastructure for a portfolio-scale deployment.

Bug found — hardcoded localhost

The dashboard's API address was hardcoded as http://localhost:8000. That's correct when the browser and the API run on the same machine, but breaks the moment the dashboard is loaded from a remote server: "localhost" in that JavaScript means the viewer's own laptop, not the server it was served from. This bug was invisible for the entire project until the exact moment a real remote deployment was attempted.

Fix

Derive the API address dynamically from window.location.hostname at runtime, so it resolves correctly whether the page was loaded from localhost or a real server's IP.

Bug found — CORS hardcoded to localhost

The API's CORS policy only allowed http://localhost:3000 as an origin. Once the dashboard was served from a different address, every request from it would have been silently rejected by the browser's CORS check.

Fix

Widened to allow all origins for this single-tenant demo deployment — an acceptable simplification given the project's actual scope, not a production multi-tenant security posture.

Infrastructure notes

  • Security group opened ports 22 (SSH), 8000 (API), and 3000 (dashboard).
  • SSH access is key-pair only, no password auth — the default and the safer option even with the security group open to all IPs.
  • An AWS budget alert was configured to email at a low spend threshold as an early warning, separate from (and cheaper to check than) manually watching the AWS bill.
  • HTTPS was deliberately not pursued for this deployment — it would require owning a domain name (recurring cost) and a reverse proxy with a TLS certificate, real infrastructure work disproportionate to a demo instance meant to be spun up and torn down. Certificate authorities won't issue a trusted cert for a bare IP address at all.

Interview Q&A

Questions this project is likely to invite, with the answer already worked out.

Why Redis instead of just using Postgres for the queue?

Redis is purpose-built for exactly this: fast in-memory operations, native list and sorted-set data structures that map directly onto "a queue" and "a delayed schedule," and atomic counters for rate limiting. Polling a Postgres table for "unprocessed rows" works but adds real load to the same database handling all the relational data, and doesn't have a clean native primitive for delayed retries the way a sorted set does.

How do you prevent duplicate webhook deliveries?

Two separate mechanisms, for two separate failure modes. Idempotency keys prevent a client from accidentally creating the same event twice (enforced by a database unique constraint, safe under concurrent requests). Separately, the atomic ZREM-as-claim pattern in the retry-promotion logic prevents two workers from both delivering the same already-queued job.

What happens if a worker crashes mid-delivery?

Honestly: that job is lost right now. BRPOP removes it from the queue the instant it's picked up, before processing finishes, so a crash between pop and commit means no other worker will ever see it again. The correct production fix is a visibility-timeout pattern (move to a per-worker in-progress list on pop, sweep stale entries back onto the queue after a timeout) — not implemented here, and a good example of a real, named tradeoff rather than an unknown gap.

What was the hardest bug you found?

The multi-replica startup deadlock in Phase 12. Every worker independently ran schema setup at startup; scaling to 8 replicas caused all of them to collide on a Postgres DDL lock simultaneously, which deadlocked, which crashed every worker with no restart policy in place — and the failure mode looked like nothing at all was happening, not like an error. Diagnosing it meant checking container statuses, reading the actual Postgres error message, and reasoning through why 8 simultaneous "check if the table exists" operations could deadlock at all.

How would you scale this further?

Horizontally on the worker side, which is already proven safe (Phase 6). On the API side, more uvicorn processes or more container replicas behind a load balancer. On the database side, the connection pool tuning from Phase 12 would need revisiting again at a larger scale, and a managed Postgres (RDS) with read replicas would be the next real step. The retry visibility-timeout gap from Phase 6 would also need addressing before scaling workers much further under real production traffic.

Why backoff between retries instead of retrying immediately?

An immediate retry against a downstream service that's struggling (rate-limited, overloaded, mid-restart) just adds more load to something already failing, and wastes a retry attempt on a problem that hasn't had time to resolve. Backoff gives the destination time to recover. The schedule (5s/30s/120s) is a hand-picked increasing sequence, not a true exponential formula — it's predictable and easy to demo, at the cost of not following a strict constant-ratio curve the way "exponential backoff" technically implies.

Known limitations

Said out loud, on purpose — naming these is more credible than pretending they don't exist.

  • Event creation and queueing aren't atomic — found under load testing (Phase 12, Bug 4). An interruption between the Postgres commit and the Redis push can silently orphan an event before it's ever queued.
  • No worker crash-recovery (visibility-timeout) pattern — a job popped from the queue is lost if the worker dies before finishing it.
  • HMAC signing uses one global secret per instance, not a secret per registered destination (no endpoint-registration concept exists).
  • Rate limiting uses a fixed window, which allows a small burst at the window boundary; a sliding window or token bucket would smooth that at the cost of needing a Lua script to stay atomic.
  • No HTTPS on the AWS deployment — a deliberate scope decision for a demo instance, not an oversight.
  • No automated test suite; CI verifies the Docker images build (and the dashboard's TypeScript compiles) but doesn't execute or test the Python application code.
